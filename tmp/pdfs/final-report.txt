Toothpick vector construction
How the recognisable pointed stroke is generated and how weight changes without erasing the identity.

The canonical geometry
Glyphs are stored as skeletal line segments, not pre-expanded outline drawings. Every segment has a start point,
end point, and direction. The builder converts the segment into a six-point polygon: a point at the start, two body
corners around the start side, a point at the end, and two body corners around the end side. This is the toothpick
silhouette.
For a segment from A to B:
1. Compute direction d = normalize(B - A).
2. Compute perpendicular n = (-d.y, d.x).
3. Choose body width w from the current master.
4. Choose taper length t = min(segment_length * 0.32, max(w * 1.55, 24)).
5. Emit six compatible points around A + d*t and B - d*t.
6. Close the polygon and preserve overlap in the variable source.

Why this survives bold weights
- The skeleton stays fixed; density grows perpendicular to the stroke.
- The taper cap is bounded by segment length so it cannot consume short segments.
- The taper scales with body width but has a floor, preserving visible points in Fine.
- All four masters use compatible contour order and point topology.
- Static instances remove overlaps; the variable font keeps compatible overlaps and sets overlap flags.

What went wrong in the old behavior
A naive bolding method expands every dimension equally. That rounds or blunts the tips, makes bowls look inflated,
and allows intersections to dominate the skeleton. The repaired build increases body width while bounding taper
length. This preserves the sharp toothpick terminal at 700 Structural.
Model instruction
Do not use CSS text-shadow, stroke, transform scale, synthetic bold, or browser font-synthesis to create
heavier weights. A weight must be a real interpolated master result.

Explicit sidebearings
The old mathematical centering and special T/r/t width patch were removed. Every glyph now receives an explicit left
sidebearing and a resulting advance. Spacing is optical: round forms, diagonals, narrow stems, punctuation, and
combining marks cannot be centered by one formula.
- Advance widths are identical at 100, 300, 500, and 700 unless a width-changing exception is documented. The current
exception set is empty.
- Known problem groups are reviewed as systems: T/t/r/f/j; A/V/W/Y; b/d/h/n/p/q; a/e/o/s; punctuation around rounds,
diagonals, and narrow forms.
- Website letter-spacing workarounds were removed so every proof shows the font's real spacing.

Kerning
GPOS class kerning was added and verified through HarfBuzz. The proof set includes AV, AW, AT, FA, LT, PA, TA,
To, Te, Ty, Tr, Va, Wa, Yo, rt, and ry. A passing test requires the shaped advance with kerning enabled to be smaller
than the same pair with kerning disabled.
Critical gotcha
Sidebearings solve default spacing; kerning solves exceptional pair relationships. Do not use kerning to repair
a globally bad sidebearing, and do not change a sidebearing to fix one isolated pair.

Lowercase harmony and loop closure
How the repeated bowl system was regularised without making every letter a copy of o.

Shared structural rule
The repaired lowercase uses one shared vertical language but preserves letter-specific anatomy. The loop-bearing
family b, d, h, p, and q shares a documented secondary closure level. Ascenders reach 720, lowercase bodies
occupy the 520 x-height zone, and descenders reach -220 where applicable.
Glyph

Primary distinction

Does it read as a, not a modified o?

Does the curve close below x-height?

Right ascender plus lower bowl

Is it a mirrored system, not an oversized loop?

h

k

Ascender reaches cap height; clean diagonals

Does it avoid looking like an enlarged x-height k?

Inspection protocol
For each glyph in b d h n p q a e o s g k:
- render at weights 100, 300, 500, 700
- render at sizes 12, 14, 16, 24, 48, 96, 160 px
- compare cap height, x-height, baseline, descender, and closure guide
- compare beside H O n o and inside words
- reject if the identity depends on specimen CSS

Why the inspector matters
The site inspector is a diagnostic view, not the source of truth. It overlays the declared metric guides, uses
arrow-key/Home/End navigation, and exposes all non-whitespace, non-combining glyphs from the generated
character-set manifest. On small screens, labels move into a two-column block above the SVG so they cannot
overlap the drawing.

Latin Core and marks
The repertoire was expanded from a display subset to the exact Google Fonts Latin Core set.

Coverage contract
The build embeds the exact 319-codepoint GF Latin Core repertoire. The generated Strawn-Character-Set.json is
versioned and consumed by the website. Tests compare the font cmap against the expected set and fail on one
missing or extra codepoint.

Construction strategy
- Base Latin glyphs are drawn from canonical Strawn skeletons.
- Accented letters are composites assembled from base glyphs and reusable marks.
- Combining marks are spacing-aware during construction and are exposed with mark anchors.
- Special letterforms such as AE/ae, Eth, Oslash, Thorn, Eszett, Lslash, OE/oe, Dcroat, Hbar, and dotless i/j receive
explicit constructions.
- GSUB ccmp supports canonical composition; GPOS mark and mkmk position marks and stacked marks.

Language proof set
Proof English, French, German, Spanish, Portuguese, Italian, Dutch, Polish, Czech, Slovak, Hungarian, Romanian,
Danish, Norwegian, Swedish, Finnish, and Icelandic. A proof passes only if shaping maps every codepoint to a
non-.notdef glyph and marks are positioned without fallback.
Critical gotcha
A glyph appearing in the cmap is not enough. It can still have broken anchors, incorrect decomposition,
missing advance, bad mark stacking, or browser fallback. Test shaping and inspect language strings.

Manifest use in the website
import characterSet from './Strawn-Character-Set.json';

.filter(name is not COMBINING)
.map(character)
.filter(non-whitespace);

.map(combining marks with a non-breaking-space carrier)

Static versus variable overlap policy
Compatible overlapping contours remain in the variable font and are marked with the overlap flag. Static instances
are generated through FontTools varLib instancing and then flattened with skia-pathops. Do not remove overlaps
from masters before interpolation: contour compatibility can be destroyed.

Maintenance and next release
How to change Strawn again without reintroducing the defects repaired in v0.7.

When editing one glyph
- Edit its canonical skeleton and explicit sidebearing in scripts/build.py.
- Review the related family, not the isolated glyph.
- Check all four masters and the interpolation between them.
- Re-run pair proofs if the glyph participates in kerning.
- Rebuild every artifact and recopy the website WOFF2/manifest.
- Bump version only when artifacts and manifests agree.

When adding a character
- Add the Unicode codepoint to the declared repertoire.
- Prefer components for accents and anchors for marks.
- Add language and shaping proofs.
- Update the expected cmap count only after exact set comparison passes.

When adding an axis
Do not bolt an axis onto existing masters. Define compatible source geometry, axis mapping, STAT values,
instances, test matrices, and product CSS defaults first. Width, grade, optical size, and italic remain out of scope for
v0.7.

Versioning policy
- Patch: metadata, documentation, or non-layout correction.
- Minor: new characters, features, or outline/spacing changes that can reflow text.
- Major: incompatible family/axis redesign or removal of supported behavior.
Rollback
Keep v0.6 tagged and downloadable. Never overwrite a released binary under an existing version tag.
